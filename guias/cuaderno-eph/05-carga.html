5  Carga masiva

Las tablas están creadas y vacías. En este capítulo cargamos los datos en bloque y los pasamos al modelo, todo con SQL. Es lo que vimos en la presentación C03-2 con COPY, ahora con un millón y medio de filas.

5.1 Conseguir los datos

Los dos archivos, hogares.csv y personas.csv, están listos en la carpeta datos del Drive del curso, comprimidos en hogares.zip y personas.zip. Bajalos y descomprimilos en una carpeta llamada eph. Desde acá todo es SQL.

Si te interesa cómo se armaron esos archivos a partir de las bases que publica INDEC, está en el apéndice A.

5.2 La ruta de los archivos

Para cargar un archivo hay que decirle a PostgreSQL dónde está, con su ruta completa. Es el error más común de este capítulo, así que vale la pena detenerse.

La ruta completa empieza desde la raíz del disco:

Sistema Ejemplo
Windows C:/Users/ana/Downloads/eph/hogares.csv
Mac /Users/ana/Downloads/eph/hogares.csv

Dos formas de conseguirla sin tipearla:

  • En Windows, con Shift y clic derecho sobre el archivo, Copiar como ruta de acceso.
  • En Mac, con clic derecho sobre el archivo y la tecla Opción apretada: Copiar «hogares.csv» como nombre de ruta.
TipComillas en Windows

Copiar como ruta de acceso trae la ruta entre comillas dobles. En COPY y \copy la ruta va entre comillas simples, así que hay que cambiarlas. Las barras invertidas, como en el ejemplo de C03-2 (C:\sampledb\persons.csv), funcionan igual que las comunes.

5.3 COPY y \copy

Las dos leen un archivo y lo cargan en una tabla, con la sintaxis de C03-2: DELIMITER ',' indica el separador y CSV HEADER, que el archivo es un CSV con los nombres de las columnas en la primera línea. La diferencia es quién lee el archivo:

  • COPY es una sentencia SQL y la ejecuta el servidor. El archivo tiene que estar en la máquina del servidor y el servidor necesita permiso para leerlo. En Windows, el servicio de PostgreSQL corre con un usuario del sistema que no puede entrar a tu carpeta de descargas, y COPY falla con Permission denied.
  • \copy es un comando de psql, el cliente. Lee el archivo con tus permisos y le manda los datos al servidor. Por eso casi siempre funciona.

\copy se escribe en psql (en Windows, SQL Shell (psql); en pgAdmin, Tools y luego PSQL Tool). No es SQL, así que no funciona en el Query Tool. Si preferís no salir de pgAdmin, el menú Import/Export Data… de cada tabla hace lo mismo con una ventana: formato csv y la opción Header activada.

5.4 Primero, a una tabla de staging

Los archivos no se cargan directo en hogares y personas. Primero van a tablas de staging (de carga intermedia) con las mismas columnas que el CSV, todas de tipo texto. Hay buenas razones:

  • Los archivos tienen sorpresas. Los montos mezclan coma y punto decimal, en algunos trimestres vienen en notación científica (9e+05) y la falta de respuesta se codifica con -9. Con columnas de texto la carga nunca falla por eso.
  • La limpieza queda escrita en SQL, a la vista, en vez de esconderse en un programa aparte.
  • Antes de pasar los datos al modelo podemos verificarlos con consultas.

Las nombramos con el prefijo stg_ para distinguirlas de las tablas del modelo:

CREATE TABLE stg_hogares (
    codusu text, ano4 text, trimestre text, nro_hogar text,
    region text, aglomerado text, pondera text, ii7 text,
    ix_tot text, itf text, ipcf text, pondih text
);

CREATE TABLE stg_personas (
    codusu text, ano4 text, trimestre text, nro_hogar text, componente text,
    region text, aglomerado text, pondera text,
    ch03 text, ch04 text, ch06 text, nivel_ed text, estado text,
    p21 text, p47t text, itf text, ipcf text
);

Ahora sí, la carga. Elegí la pestaña de tu sistema y cambiá ana por tu usuario:

  • Windows
  • Mac
\copy stg_hogares  FROM 'C:/Users/ana/Downloads/eph/hogares.csv'  DELIMITER ',' CSV HEADER
\copy stg_personas FROM 'C:/Users/ana/Downloads/eph/personas.csv' DELIMITER ',' CSV HEADER
\copy stg_hogares  FROM '/Users/ana/Downloads/eph/hogares.csv'  DELIMITER ',' CSV HEADER
\copy stg_personas FROM '/Users/ana/Downloads/eph/personas.csv' DELIMITER ',' CSV HEADER

Cada \copy responde con la cantidad de filas cargadas. Lo confirmamos:

SELECT 'stg_hogares' AS tabla,
       COUNT(*) AS filas
FROM stg_hogares
UNION ALL
SELECT 'stg_personas',
       COUNT(*)
FROM stg_personas;
2 filas
tabla filas
stg_hogares 551081
stg_personas 1634288

5.5 ¿Se cumplen las dependencias?

En el capítulo 3 normalizamos a partir de dependencias funcionales que dedujimos del dominio. Con los datos cargados las podemos comprobar. La idea es siempre la misma: agrupar por el lado izquierdo de la dependencia y buscar grupos con más de un valor del lado derecho. Si no aparece ninguno, la dependencia se cumple.

¿Cada vivienda está en un solo aglomerado?

SELECT codusu,
       COUNT(DISTINCT aglomerado) AS aglomerados
FROM stg_hogares
GROUP BY codusu
HAVING COUNT(DISTINCT aglomerado) > 1;
0 filas
codusu aglomerados

¿Cada aglomerado está en una sola región?

SELECT aglomerado,
       COUNT(DISTINCT region) AS regiones
FROM stg_hogares
GROUP BY aglomerado
HAVING COUNT(DISTINCT region) > 1;
0 filas
aglomerado regiones

¿El ponderador que se repite en cada persona es el de su hogar?

SELECT COUNT(*) AS personas_con_otro_ponderador
FROM stg_personas p
INNER JOIN stg_hogares h ON h.codusu = p.codusu AND h.ano4 = p.ano4
                        AND h.trimestre = p.trimestre AND h.nro_hogar = p.nro_hogar
WHERE p.pondera <> h.pondera;
1 fila
personas_con_otro_ponderador
0

Las tres dependencias se cumplen. Ahora, el costo de la redundancia. El ingreso total familiar está guardado dos veces, en el archivo de hogares y en cada persona del archivo de personas. ¿Dicen lo mismo? Lo comparamos como número, porque el mismo monto puede venir escrito 900000 en un archivo y 9e+05 en el otro:

SELECT p.codusu,
       p.ano4,
       p.trimestre,
       p.nro_hogar,
       MIN(h.itf) AS itf_archivo_hogares,
       MIN(p.itf) AS itf_archivo_personas
FROM stg_personas p
INNER JOIN stg_hogares h ON h.codusu = p.codusu AND h.ano4 = p.ano4
                        AND h.trimestre = p.trimestre AND h.nro_hogar = p.nro_hogar
WHERE REPLACE(p.itf, ',', '.')::numeric <> REPLACE(h.itf, ',', '.')::numeric
GROUP BY p.codusu, p.ano4, p.trimestre, p.nro_hogar;
1 fila
codusu ano4 trimestre nro_hogar itf_archivo_hogares itf_archivo_personas
TQRMNOQQWHJMKSCDEGJBF00793251 2023 4 1 1900000 1500000

Un hogar, en el cuarto trimestre de 2023, tiene dos ingresos distintos según el archivo que se mire. ¿Cuál es el verdadero? Con los datos guardados una sola vez, esa pregunta no podría aparecer.

El otro caso es un atributo derivado. IX_TOT dice cuántos miembros tiene el hogar, algo que también se puede contar:

SELECT h.codusu,
       h.ano4,
       h.trimestre,
       h.nro_hogar,
       h.ix_tot,
       COUNT(*) AS personas_en_la_base,
       h.itf,
       h.ipcf
FROM stg_hogares h
INNER JOIN stg_personas p ON p.codusu = h.codusu AND p.ano4 = h.ano4
                         AND p.trimestre = h.trimestre AND p.nro_hogar = h.nro_hogar
GROUP BY h.codusu, h.ano4, h.trimestre, h.nro_hogar, h.ix_tot, h.itf, h.ipcf
HAVING h.ix_tot::integer <> COUNT(*);
1 fila
codusu ano4 trimestre nro_hogar ix_tot personas_en_la_base itf ipcf
TQRMNOPYUHKLLMCDEHIBB00654657 2021 1 1 4 3 90000 30000

En un hogar de 2021, IX_TOT dice 4 pero hay 3 personas. El propio INDEC calculó el ingreso per cápita dividiendo por 3 (90.000 / 3 = 30.000), o sea, contando. Por eso en nuestra base la cantidad de miembros no se guarda: se cuenta.

5.6 Del staging al modelo

Con INSERT ... SELECT las filas pasan de las tablas de staging a las definitivas, convertidas y limpias. El orden importa por las claves foráneas: primero viviendas, después hogares, al final personas.

Las viviendas son los valores distintos de codusu, cada uno con su aglomerado:

INSERT INTO viviendas (codusu, id_aglomerado)
SELECT DISTINCT codusu,
       aglomerado::smallint
FROM stg_hogares;

Los hogares necesitan tres arreglos además de convertir tipos:

  • II7 vale 0 en algunos hogares, y 0 no es un código del diseño de registro: lo guardamos como NULL.
  • Algunos montos traen coma decimal; REPLACE la cambia por punto antes de convertir a numeric, que además entiende la notación científica.
  • Un hogar que no respondió sus ingresos figura con ITF en 0 y PONDIH en 0. Ese cero no es un ingreso de cero pesos: es un dato que falta, y en SQL un dato que falta es NULL.
INSERT INTO hogares (codusu, anio, trimestre, nro_hogar, id_tenencia,
                     ingreso_total_familiar, pondera, pondih)
SELECT codusu,
       ano4::smallint,
       trimestre::smallint,
       nro_hogar::smallint,
       NULLIF(ii7, '0')::smallint,
       CASE WHEN REPLACE(itf, ',', '.')::numeric = 0 AND pondih = '0' THEN NULL
            ELSE REPLACE(itf, ',', '.')::numeric
       END,
       pondera::integer,
       pondih::integer
FROM stg_hogares;

En las personas, la edad -1 significa «menos de un año» y pasa a 0, y el código -9 de los ingresos (no sabe o no responde) pasa a NULL:

INSERT INTO personas (codusu, anio, trimestre, nro_hogar, componente,
                      id_parentesco, sexo, edad, id_nivel_educativo,
                      id_condicion_actividad, ingreso_ocupacion_principal,
                      ingreso_total_individual)
SELECT codusu,
       ano4::smallint,
       trimestre::smallint,
       nro_hogar::smallint,
       componente::smallint,
       ch03::smallint,
       ch04::smallint,
       GREATEST(ch06::smallint, 0),
       nivel_ed::smallint,
       estado::smallint,
       NULLIF(REPLACE(p21, ',', '.')::numeric, -9),
       NULLIF(REPLACE(p47t, ',', '.')::numeric, -9)
FROM stg_personas;

Mientras se insertan las filas, PostgreSQL controla cada restricción del capítulo 4: que el hogar exista para cada persona, que los códigos estén en sus catálogos, que el trimestre vaya de 1 a 4. Si un solo dato no cumple, el INSERT entero se cancela.

5.7 Control final

SELECT 'viviendas' AS tabla, COUNT(*) AS filas FROM viviendas
UNION ALL
SELECT 'hogares', COUNT(*) FROM hogares
UNION ALL
SELECT 'personas', COUNT(*) FROM personas;
3 filas
tabla filas
viviendas 196057
hogares 551081
personas 1634288

Las filas coinciden con las de staging: 551.081 hogares y 1.634.288 personas, en 196.057 viviendas. El staging ya cumplió su función:

DROP TABLE stg_hogares, stg_personas;
ANALYZE;

ANALYZE actualiza las estadísticas que usa PostgreSQL para decidir cómo ejecutar cada consulta. Conviene correrlo después de una carga grande.

5.8 Los scripts

Todo lo que hicimos para armar la base está también en cuatro scripts, uno por grupo de tablas. Sirven para rehacerla sin ir bloque por bloque, entera o por partes:

Script Qué hace Dónde se corre
01_codigos.sql Crea regiones, aglomerados y catálogos, con sus datos Query Tool o psql
02_hogares.sql Carga hogares.csv y arma viviendas y hogares psql
03_personas.sql Carga personas.csv y arma personas psql
04_vistas.sql Crea las vistas del capítulo 6 Query Tool o psql

Los que cargan archivos usan \copy, así que van en psql. Guardá los scripts en la carpeta eph, junto a los CSV. En psql, \c te conecta a la base, \cd te lleva a la carpeta y \i ejecuta cada script:

  • Windows
  • Mac
\c eph
\cd C:/Users/ana/Downloads/eph
\i 01_codigos.sql
\i 02_hogares.sql
\i 03_personas.sql
\i 04_vistas.sql
\c eph
\cd /Users/ana/Downloads/eph
\i 01_codigos.sql
\i 02_hogares.sql
\i 03_personas.sql
\i 04_vistas.sql
TipBarras en \cd

En \cd, a diferencia de \copy, las barras invertidas no funcionan: la ruta va con barras comunes, como en el ejemplo. Si tiene espacios, entre comillas simples.

Para correr los cuatro de una vez está eph_completo.sql: después del \cd, \i eph_completo.sql. Tarda un par de minutos.

Cada script empieza borrando lo que va a crear, así que se puede volver a correr. Pero el DROP ... CASCADE del principio también se lleva las claves foráneas y las vistas que dependían de esas tablas. Por eso, si volvés a correr un script, corré también los que le siguen.
